# AI Workflow

## Tools used

- **Claude Code** (VS Code extension, model Claude Sonnet 5.5) wrote the code, tests, scripts and documentation in this repo.
  Every commit carries a `Co-Authored-By: Claude` trailer.
- The Next.js docs bundled in `node_modules` (the installed Next 16.4.6 differs from what the model knew, and the project's
  `AGENTS.md` points at them), and Neon's CLI and agent skills for connection and driver advice.
- Vitest for unit tests, and `playwright-core` driving my installed Microsoft Edge for browser checks and screenshots.

## How I worked

I gave Claude the project in steps, each a written spec with the scope, hard rules ("free tiers only", "never print or commit
credentials", "do not build X yet") and what to verify. The git history follows those steps: scaffold; cleanup and permission
tests; database, seed, auth and API; list, editor and autosave; import and sharing; polish and deploy readiness; submission.
I reviewed each step's report before giving the next one. I ran the app myself (for example, I pasted the dev-server error that
led to the `/` redirect fix), applied the migration to my Neon database, deployed to Vercel and created the GitHub repository.

## What I decided and what I delegated

- **I decided:** the stack and the free-tier-only constraint; mock cookie login with seeded users as a deliberate cut; the roles
  (owner, editor, viewer) and the status-code policy (404 when you have no access, 403 when you can see it but not change it);
  turning Cache Components off; the import types and the 2 MB limit; that unsupported content must be dropped by the editor
  schema; the rule that the e2e suites only run against localhost; and what each step was *not* allowed to build yet.
- **I delegated, and reviewed:** the implementation, the test design, the autosave state machine, the share dialog, the e2e
  suites, and some decisions I explicitly handed over ("you decide": removing the unused Neon platform files).

## Where the first answer was wrong, and what caught it

- The first permission code treated an unknown share value as viewer access. While writing the permission tests Claude added a
  "fails closed" test, which failed 5 of 5; the function was then fixed.
- A fuzz suite found three real 500s or bad acceptances (NUL characters, deep nesting, malformed URLs) that normal tests had missed.
- For oversized uploads, Claude's first fix made things worse (truncated responses); it was reverted and replaced. For the 404
  page, its first explanation was wrong; a control page showed it is Next's behaviour.
- Tests passed while two things were still wrong: the proxy added for URL errors was also buffering uploads (only visible in the
  server log), and screenshots showed cramped or jammed layouts that no assertion covered.
- Many failing e2e checks were mistakes in the scripts Claude wrote, not in the app; they were fixed in the scripts, not
  loosened.
- A real connection string ended up in my working copy of `.env.example`. It was flagged, never committed, and every push was
  preceded by a scan of all history.

## Reflections

AI made it possible to build and test a lot quickly, but its first answer was often confident and incomplete. What worked was
making it prove things: tests that fail first, mutation checks, a real browser, screenshots, server logs, and a fresh-clone run.
I trust the parts that have tests or e2e checks behind them. I am less sure of what was never tried: Chrome, Firefox and Safari,
real phones, screen readers, and unusual `.docx` files. I did not measure how much time AI saved, so I make no claim about it.
